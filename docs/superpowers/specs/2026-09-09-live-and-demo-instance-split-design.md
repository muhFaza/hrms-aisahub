# Splitting HRMS into a live instance and a demo instance

**Date:** 2026-09-09
**Status:** design approved, not yet implemented

## Context

Ayu (Aisahub's HR) wants to start using the HRMS for real. The thesis
*"Rancang Bangun Sistem Human Resource Management Menggunakan PERN Stack"* still
needs a working demo instance for testing and for the defence.

Today there is exactly one deployment — `hrms.muhammadfaza.com`, served from
`~/hrms/` on the VPS — and it holds a demo dataset generated by
`scripts/demo-data.ts` (wiped and rebuilt 2026-08-06 for the demo video).

The original proposal was two long-lived git branches, one per environment, each
with its own deployment and subdomain.

## Decision: split on configuration, not on code

**One branch (`main`), one image, two instances differentiated by environment
variables.** There is no `demo` branch.

Everything that makes the current deployment a "demo" is already configuration or
data, not code:

1. `SEED_ON_START=true` — an environment variable
2. `scripts/demo-data.ts` — a script run by hand
3. The click-to-login account list in `client/src/pages/LoginPage.tsx:23-29`

A branch-per-environment split was rejected for three reasons:

- **Divergence tax.** Every fix and every thesis revision would need merging
  twice, forever, and the branches drift apart in between.
- **Defensibility.** The system demonstrated at the defence should be the same
  commit that runs Aisahub's payroll. Branch drift makes "is this the real
  system?" a question with a complicated answer.
- **Safety.** The demo login list renders a shared password on screen
  (`LoginPage.tsx:177`). A branch can be merged in the wrong direction by a
  human; an environment variable read at runtime cannot. This widget must never
  appear in front of real salary data.

## Topology

| | Demo (thesis) | Live (Aisahub) |
| --- | --- | --- |
| Host | `hrms.muhammadfaza.com` *(unchanged)* | `hr.muhammadfaza.com` *(new)* |
| Server directory | `~/hrms/` *(unchanged)* | `~/hrms-live/` |
| Containers | `hrms-app`, `hrms-db` | `hrms-live-app`, `hrms-live-db` |
| Internal network | `hrms-internal` | `hrms-live-internal` |
| Volumes | `hrms-db-data`, `hrms-uploads` | `hrms-live-db-data`, `hrms-live-uploads` |
| `mem_limit` | app 192m, db 160m | app 192m, db 160m (mirrors demo) |
| `DEMO_MODE` | `true` | `false` |
| `SEED_ON_START` | `true` | `false` |
| `BOOTSTRAP_ON_START` | `false` | `true` |
| Data | existing demo dataset, untouched | empty; Ayu enters everyone via the UI |
| Backups | none | nightly `pg_dump`, 14 retained |

The demo keeps the existing URL so the recorded video, the skripsi document and
any UAT screenshots stay valid. `hr.muhammadfaza.com` needs no DNS work — the
wildcard `*.muhammadfaza.com` A record already points at this box, and Traefik
routes purely from container labels.

A separate Postgres container for live, rather than a second database inside
`hrms-db`. It costs roughly 10-15MiB. In exchange, no connection string, script
or mistake on the demo side can reach live payroll data. On real salary data
that is worth 15MiB.

## Isolation rules

### 1. Distinct `JWT_SECRET` per instance — mandatory

`middleware/auth.ts` takes only `userId` from the token and re-reads the role
from the database on every request. If both instances share a secret, a token
minted by the demo's `hr@aisahub.com` — whose password is printed on the demo
login page — is a structurally valid token for user ID 1 on the live instance,
which will be Ayu's HR account.

Sharing the secret is a full authentication bypass into real payroll, reachable
by anyone who reads the demo login screen. The two `.env` files must carry
independently generated secrets.

### 2. `DEMO_MODE` is read at runtime, never baked at build

One image serves both instances, so a Vite build-time flag cannot work. A public
`GET /api/v1/config` returns `{ "demoMode": boolean }`; the login page hides the
account list when it is false. The endpoint is unauthenticated by necessity — it
is consumed before login — and exposes exactly one boolean.

### 3. The bootstrap path can never delete

`seed.ts` opens with `deleteMany()` across all 11 tables. The live instance must
have no code path that can reach it. The bootstrap module lives in its own file,
never imports `seed.ts`, and contains no delete operation of any kind.

## Prerequisite: retire umami

The VPS cannot fit the live instance as it stands.

| | Value |
| --- | --- |
| `available` today | 210MB |
| Live instance needs | ~65MB (app ~50MiB + near-empty db ~15MiB) |
| `available` after | ~145MB |
| CI gate in `deploy.yml` | fails below 150MB |

The gate is a single step in a single job, so tripping it blocks deploys to
**both** instances, not just the new one.

Extending swap does not solve this. `free -m`'s `available` column counts only
RAM — free pages plus reclaimable page cache — and reports swap separately. A
larger `/swapfile` leaves `available` at 210MB and the gate trips identically.
It buys OOM-kill resilience, not headroom, and swapping a Postgres holding real
payroll is the specific failure mode to avoid.

**umami is the source of the memory.** At 108.5MiB plus 17.2MiB for `umami-db`
it is the largest consumer on the box, and it is the one service that never got
a `mem_limit` — it runs against the full 965MB, in violation of the box's own
hard constraint. It grew 58.3 → 108.5MiB inside 70 minutes of observation.
Uncapped, it is the largest OOM risk on the box independent of anything here.

Removing it frees ~126MB, taking `available` to roughly 336MB and leaving ~271MB
after the live instance.

Teardown follows the verified sequence in the server's `~/CLAUDE.md`
("Checklist for tearing something down"), with one addition **before** step 1:

```sh
# Credentials live in ~/umami/.env. Check the exact variable names there first —
# stock umami images configure Postgres via DATABASE_URL, not POSTGRES_USER/DB.
docker exec umami-db pg_dump -U <user> <db> | gzip > ~/umami-final-2026-09-09.sql.gz
```

The analytics history is not recoverable otherwise. Steps then proceed as
documented: `docker compose down` in `~/umami/`, remove the images, remove the
directory, verify the Traefik router count drops to zero, and move the entry to
"REMOVED entirely" in the server's `~/CLAUDE.md`. **Step 4 does not apply** —
`analytics.muhammadfaza.com` resolves through the wildcard record, not its own A
record, so there is nothing to delete at the registrar. It will 404 once the
container is gone.

The volume `umami_umami-db-data` is not removed by `docker compose down`; drop it
explicitly only after the dump is verified.

## Deploy and CI

### Compose files

- `docker-compose.prod.yml` → renamed `docker-compose.demo.yml`, gains
  `DEMO_MODE=true` and `BOOTSTRAP_ON_START=false`
- `docker-compose.live.yml` — new, per the topology table above

### Workflow (`.github/workflows/deploy.yml`)

The image is built and shipped **once**. Both compose files reference
`image: hrms-app:deploy`, so a single `docker load` feeds two
`docker compose up -d` invocations against `~/hrms/` and `~/hrms-live/`.

Changes:

1. Tag the outgoing image `hrms-app:previous` before loading the new one, so
   rollback is a retag. This matters more now that one instance holds real
   payroll. (fazakit already works this way.)
2. Deploy to `~/hrms-live/` unconditionally.
3. Wrap the demo deploy in `if: vars.DEPLOY_DEMO != 'false'`, a GitHub repository
   variable. Flip it to `false` for defence week and the demo container keeps
   running the image it already has; its database and uploads volume are
   untouched either way. This is a switch, not a branch — no code diverges.
4. Health-check both hosts before the job reports success.
5. Leave the `free -m` gate at 150MB. With umami gone it passes at roughly
   271MB, so it keeps working as an alarm rather than an obstacle. Do not lower
   it -- the whole point of retiring umami was to avoid needing to.

`.env` files remain hand-created per directory. CI already refuses to overwrite
them and that behaviour stays.

### Environment template

`.env.docker.example` gains `DEMO_MODE`, `BOOTSTRAP_ON_START`,
`BOOTSTRAP_HR_EMAIL` and `BOOTSTRAP_HR_PASSWORD`, and drops `OWNER_EMAIL` —
which is dead config. It is plumbed through `docker-compose.prod.yml:31` and
`.env.docker.example:27` but nothing under `server/src` reads it;
`handbook/domain-rules.md:629` already records that the Owner account was removed.

## Bootstrap path

With `SEED_ON_START=false` the live database comes up with no `Role` rows and no
users. There is no way to log in and nothing to create the first account with —
`seed.ts:100-105` is currently the only code that ever creates the `HR` and
`EMPLOYEE` roles. This is the only new backend code the split requires.

New `server/prisma/bootstrap.ts`:

- Upserts the `HR` and `EMPLOYEE` roles by name
- Creates one HR user from `BOOTSTRAP_HR_EMAIL` and `BOOTSTRAP_HR_PASSWORD` at
  bcrypt cost 10, with **no `Employee` record** — matching how `seed.ts:105`
  already creates HR
- Runs only when the user count is zero; otherwise logs and exits cleanly
- Idempotent, and contains no delete of any kind
- Never imports `seed.ts`

`docker-entrypoint.sh` gains a `BOOTSTRAP_ON_START` branch reusing the existing
three-way exit-code check, so a failed probe is fatal rather than silently
skipped — the same reasoning already documented for the seed check.

Ayu changes the password through the self-service flow added in PR #10, after
which `BOOTSTRAP_HR_PASSWORD` is removed from `~/hrms-live/.env`. No forced-change
screen: that is new code for a one-time event.

## Backups

The live database gets `~/hrms-live/backup.sh`, run nightly by cron. Confirm the server clock first: cron uses the host timezone,
and the box has been assumed UTC elsewhere -- `timedatectl` before writing the
schedule, so "overnight" means overnight in Jakarta.

```sh
docker exec hrms-live-db pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB" \
  | gzip > ~/hrms-backups/hrms-live-$(date +%F).sql.gz
find ~/hrms-backups -name 'hrms-live-*.sql.gz' -mtime +14 -delete
```

`pg_dump` runs inside the container, so nothing new is installed on the box.
Disk is not a constraint at 34G free.

**The first backup must be restored into a throwaway database once, before Ayu
enters real data.** An untested backup is not a backup.

Backups stay on the same box. This protects against the realistic failure — a
bad migration, a mistaken delete, a script pointed at the wrong database — but
not against losing the VPS. That is a knowing trade, consistent with the existing
posture on this box, and worth revisiting once a payroll month has been finalized.

## Testing

Per the repository's rules: implement first, then propose tests for review, then
run them. No test-driven development.

- **Route test** for `GET /api/v1/config` — returns the correct boolean,
  reachable without a token, reflects the environment variable. Required because
  it is a new public endpoint.
- **Service tests** for `bootstrap.ts` — creates both roles and exactly one HR
  user against an empty database; is a no-op when users already exist; leaves
  existing rows untouched. Assertions are on **stored state**, not status codes,
  per the repository's own warning that Zod strips unknown keys silently.
- **Manual verification** — the client has no test runner (no `test` script in
  `client/package.json`, no vitest). Confirm by hand that the account list is
  hidden on `hr.muhammadfaza.com` and still present on `hrms.muhammadfaza.com`.

## Out of scope

- Multi-tenancy. Two instances, not one app serving two companies.
- Any import tooling. Ayu enters employees through the existing UI; there is no
  spreadsheet import.
- A forced password-change screen.
- Off-box backup replication.
- Normalising the 11 `Muhammad Faza` commits in git history — those already carry
  the correct email and are GitHub's own web-merge commits.

## Open risks

1. **The box stays tight.** Even after retiring umami, this is a 1GB VPS running
   ten services with an OOM history. `veydar-backend` (85.7MiB) and `dockerd`
   itself (165.9MB RSS) are the next largest consumers. Re-measure before adding
   anything else.
2. **Real payroll data now lives on the box**, unencrypted at rest, on a host
   whose master SSH key (`ssh1.pem`, passwordless sudo) sits in the GitHub
   Actions secrets of a **public** repository. That was an accepted risk when the
   data was fake. It carries more weight now and should be revisited separately.
3. **Traefik's access log retains full client IPs unbounded.** Unchanged by this
   work, but it now covers requests carrying real HR sessions.
4. **`seed.ts` remains one environment variable away from the live database.**
   The empty check in `docker-entrypoint.sh` and `SEED_ON_START=false` are both
   that guard. Neither is enforced by the type system.

## Follow-up, not blocking

`docker system df` reports 6.5GB of build cache and 6.7GB of stale images
reclaimable. Disk, not RAM — it does not affect the gate, but it is free hygiene.
